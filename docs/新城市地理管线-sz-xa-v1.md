### 1.2 坐标与编码算法

**单位**：游戏格，`CFG.CELL_M = 250 m`（`config.js:12`），左上原点，**x 向东为正、y 向南为正**（指南 §3）。

**投影**（`geo_*.js` 顶层 `proj` 字段，**运行时引擎不读它**，只被 `data_*.js` 读取）：

```js
proj: { lon0, lat0, kx, ky }     // lon0/lat0 = bbox 西北角；kx/ky = 格/度
ll(lat, lon) => [ (lon - lon0) * kx, (lat0 - lat) * ky ]    // data_hz.js:7 等五城同式
```

即**等距圆柱（不随纬度修正 kx）**。已核四城：`gz {113.2, 23.215, 409.6, 443}`、`hz {120.065, 30.35, 384.65, 442.3}`。校验 `kx ≈ W/Δlon`、`ky ≈ H/Δlat`：gz W=120 → 120/409.6 = 0.293° 经度，在 23.2°N 合 102.4 km ≈ 30 km ✓；hz W=112 → 112/384.65 = 0.291°，在 30.35°N 合 96.0×0.291 = 27.96 km ≈ 28 km ✓。南北 24 km 范围内 1° 经度长度变化 <0.1%，**偏差 <30 m，远小于 1/8 格，可忽略**。

**折线编解码**（`js/geo.js:9-42`）：

```
dec(s, from):  从字符索引 from 起，每组两个 zigzag varint（每 5 位一字符，charCode-63）
               x += (r & 1) ? ~(r >> 1) : (r >> 1)     // 差分 + zigzag 有符号
               输出 Float32Array，坐标为 累积值 / 64
enc(pts):      Math.round(x*64) 后差分 zigzag，字符落在 63..94
```

- **几何精度 1/64 格 = 3.90625 m**（指南 §3 确认）
- 编码本身**无损**（往返一致）；唯一有损环节是生成期的几何简化
- 多边形环字符串**首字符必须是 `'o'`（外环）或 `'i'`（内环/孔洞）**，`dec(s, 1)` 跳过该字符（`geo.js:32 polyFeat`）

## 2. OSM 抓取可行性（实测）

### 2.1 实测数据

| 查询 | bbox (S,W,N,E) | 面积 | 耗时 | 下载 | ways | highway 分布 |
|---|---|---|---|---|---|---|
| **苏州古城小块** | 31.29, 120.58, 31.33, 120.63 | 4.76×4.43 km ≈ 21.1 km² | **243.97 s** | **2.02 MB** | 2,626 | secondary 331 / primary 160 / tertiary 210 / trunk 18 / trunk_link 19 / primary_link 19 / secondary_link 19 / **unclassified 192 / residential 431 / living_street 24** / path 71 / footway 540 / pedestrian 124 / service 318 / cycleway 19 / steps 27 |

查询式（`[out:json][timeout:180]; ( way["highway"](…); way["waterway"](…); way["railway"](…); ); out geom;`），UA 必带（`city-and-metro-map-research/1.0`），`POST --data-binary`。

**关键观察**：
1. **小块 244 s，远超「30–35 s」的既有经验**——服务端当前负载高，或古城路网极密。**任何以分钟计的等待都不可靠**，必须分块 + 断点续跑。
2. **水域多边形没被抓到**：小块里 `natural=water / landuse=reservoir / waterway=riverbank` 的 way 数为 **0**（`waterway` 只拿到 river 1 / canal 40 / stream 7）。原因是查询只匹配了 `highway|waterway|railway` 三个键。**水域多边形必须单独查**（见 §2.3 层 C）。**补充实测（冻结 bbox 的 POI 定向查询）**：named water ways 苏州 25 条 / 西安 22 条（京杭大运河两段 way、渭河 way 中心压东北角 (34.4548, 109.0650)、汉城湖/未央湖/雁鸣湖群等），**但太湖、金鸡湖、独墅湖、阳澄湖未出现在 way 结果里——它们是 multipolygon relation**。层 C 查询必须同时含 `rel["natural"="water"]` + `rel["waterway"="riverbank"]`（配 `out geom` 或 `way(r); (._;>;); out geom;` 转 way），否则三大湖直接丢失，苏州的跨湖成本机制就没有物理承载。
3. 道路几何点平均 6.6 个/way，带 name 的 1,132 个、去重 367 个名称 → `names` 表规模可控。
4. `out geom` 已内联节点坐标，无需二次查 node。

### 2.2 结论

- **单次全城抓取：不可行**。苏州全城 720 km²（冻结 bbox 30.0×24.0 km），按小块 244 s/21 km² 线性外推约 8,300 s（138 分钟），即便考虑郊区稀疏修正也需 8–15 分钟；期间任何网络波动都会前功尽弃，且超过 `[timeout:180]` 服务端上限与常规工具超时。实测全城查询在 >360 s 时被中断即为例证。
- **分块抓取：可行，推荐**。块尺寸建议 `0.06°×0.05°`（块间重叠 0.005° 防边界漏要素，编码器去重）：
  - 苏州 ≈ 5.71×5.55 km ≈ 31.7 km²（比实测小块大 1.5 倍，古城极密区风险最高）→ **每块预计 4–6 分钟、1.5–3 MB**
  - 西安 ≈ 5.52×5.55 km ≈ 30.6 km² → 同量级
  - **苏州 6×5 = 30 块**（lon 0.316°/0.055° 步进 → 6；lat 0.216°/0.045° 步进 → 5）；**西安 5×6 = 30 块**（lon 0.261° → 5；lat 0.2705° → 6）
  - 串行 2.0–3.0 小时/城；overpass 公共实例通常 2 并发 slot → **1.0–1.5 小时/城**
  - **兜底**：若单块实测 >240 s（触碰 `[timeout:180]` 服务端上限），降到 `0.04°×0.05°`（≈21.1 km²/块，与实测小块同尺寸）→ 苏州 8×5=40 块、西安 7×6=42 块
- **更稳备选（推荐优先评估）**：Geofabrik 下载 `jiangsu-latest.osm.pbf` / `shaanxi-latest.osm.pbf`，本地 `osmium extract --bbox` + `osmium export` 出 GeoJSON。只需 2 次下载、无 overpass 限流、可重复裁剪。**若团队能装 osmium，优先此路径**；否则用分块 overpass。

### 2.3 分层查询设计（每类一次查询，便于缓存/重试/并行）

按层拆查询，单次 payload 小、失败重试代价低：

| 层 | 查询 | 目标 geo 层 |
|---|---|---|
| A | `way["highway"~"^(trunk\|primary\|secondary\|tertiary)$"](bbox)` | `roads`（cls 4/3/2/2） |
| B | `way["highway"~"^(unclassified\|residential\|living_street)$"](bbox)` | `streets`（或 `roads` cls=1，见 §3.4） |
| C | `way["natural"="water"](bbox); way["landuse"="reservoir"](bbox); way["waterway"="riverbank"](bbox); rel["natural"="water"](bbox); rel["waterway"="riverbank"](bbox);` | `water` 多边形（多环 o/i）。**relation 必查**——太湖/金鸡湖/独墅湖/渭河主干都是 multipolygon（§2.1 观察 2）；relation 需 `out geom` 或 `way(r)` 转 way 后再编码 |
| D | `way["waterway"~"^(river\|canal\|stream)$"](bbox)` | `water` 河川线（宽度按 `width` tag 或类型默认）。实测京杭大运河为 way（苏州两段中心 (31.3914,120.4995)/(31.2470,120.6529)） |
| E | `way["railway"="rail"](bbox)` | `rail`（**排除 `subway`**——地铁由玩家建；`station=subway` 的节点仅供 places 参照，不进 rail 层） |
| F | `way["leisure"="park"](bbox); way["landuse"="forest"](bbox); way["natural"~"^(wood\|scrub)$"](bbox); way["boundary"="protected_area"](bbox);` | `parks` / `woods` / `reserves` |
| G | `rel["boundary"="administrative"]["admin_level"~"^(6\|7\|8)$"](bbox); out geom;` | `admin`（**行政边界多为 relation**，需 `out geom` 或 `way(r)` 转换） |
| H | `node["place"~"^(city\|town\|village\|suburb\|neighbourhood\|square)$"](bbox); out;` | `places`（name + 格坐标 + 等级）。**实测等级分布（冻结 bbox）**：苏州 town 6 / city 6 / suburb 10 / neighbourhood 7 / village 1；西安 city 7 / suburb 5 / town 1 / neighbourhood 1 / square 4 |

**工程要求**：块级 JSON 缓存到 `data/raw/<city>/<block>.json`；断点续跑；失败重试 3 次；块间重叠 0.005°；UA 必带；`[timeout:180]`；最后一次性编码合并（跨块去重）。

## 3. 原型编码器与 round-trip 结论

### 3.1 做法

`/tmp/cmgeo/encode.mjs`（一次性，**未进仓库**）：读 §2.1 的苏州古城小块 JSON → 按 `proj` 变换 → 过滤/分级 → 20 m 距离阈值抽稀 → 差分 zigzag 编码 → 输出 `geo_sz_proto.js`（挂 `CM.GEOS.szproto`）→ 用**真实 `js/geo.js`** 解回。

映射规则（原型版；cls 口径已按主理人拍板更新为**最终规则**，见 §3.4 T4）：

| OSM | geo 层 | 规则 |
|---|---|---|
| `highway` ∈ trunk/primary/secondary/tertiary（**有名**） | `roads` | cls = 4/3/2/2；`_link` 后缀 → flags bit2 |
| `highway` ∈ unclassified/residential/living_street（**有名**） | `roads` | cls = 1（承接 gz 的 cls=1 口径） |
| `highway` ∈ unclassified/residential/living_street（**无名**） | `streets` | 直接编码，`!` 拼接 |
| `highway` ∈ path/footway/pedestrian/service/cycleway/steps | **丢弃** | 与 gz 的 streets 层口径一致 |
| `waterway` ∈ river/canal/stream | `water` 河川线 | 宽度默认 river 0.09 / canal 0.05 / stream 0.03 格 |
| `natural=water` / `landuse=reservoir` / `waterway=riverbank`（**way 与 relation 都要**） | `water` 多边形 | 多环 o/i；relation 需先转 way（§2.3 层 C） |
| `railway=rail` | `rail` | flags：bridge→1、tunnel→2、embankment→4；高铁 bit4=16 + `year` |
| `bridge=yes` / `tunnel=yes` | flags bit0/bit1 | |
| 全部 roads | flags bit3=1 | 主理人拍板照 gz 惯例（§3.4 T3） |

### 4.0 换算公式与一致性自检

```js
kx = W / (lonE - lonW)                        // 格/度（经度）；ky = H / (latN - latS)
x  = (lon - lonW) * kx                        // 格，左上原点，东为正
y  = (latN - lat) * ky                        // 格，向下为正
lon = lonW + x / kx ;  lat = latN - y / ky    // 逆变换（校核 simRoads 的裸格坐标用）
```

| 自检项 | 苏州 sz | 西安 xa |
|---|---|---|
| 冻结 W×H | **120×96** | **96×120（横版转置）** |
| Δlon / Δlat | 0.316° / 0.216° | 0.261° / 0.2705° |
| 实距（中心纬度修正） | 30.03 km × 24.0 km | 24.0 km × 30.1 km |
| kx = W/Δlon | 120/0.316 = **379.75** ✓ | 96/0.261 = **367.82** ✓ |
| ky = H/Δlat | 96/0.216 = **444.44** ✓ | 120/0.2705 = **443.62** ✓ |
| 面积 | 720 km²（与 gz 同量级） | 722 km² |

冻结值内部自洽（kx/ky 与 W/H/bbox 严格互推），**无需调整**。等距圆柱在 24–30 km 南北范围内的经度修正偏差 <30 m，远小于 1/8 格（§1.2 已核）。

|---|---|---|
| lat/lon → 格坐标 | `data_hz.js:8-10` 同式 `poly()/at()/anchor()` + `ll()` | **唯一数据源是 geo 文件的 `proj`**；设计案已承诺不手写格坐标（§1.4 坐标口径），本表是其期望输出 |
| `rg.poly` 消费 | `city.js:250-254` | 绝对格坐标；支持多环 `[[[x,y],…],…]`（`rg.poly[0][0]` 非数字时判多环）；本表 §4.1.2/§4.2.2 即期望值 |
| centers 消费 | data 文件加载时 `at()` | 运行时不再换算；本表 §4.1.3/§4.2.3 用于回归比对 |
| places 命名 | `metro.js:417 M.suggestName` | 只按距离取 3.2 格（800 m）内最近的未用名；**`p[3]` level 全程不被消费**（`data_gz.js:287` 仅透传）——level 映射口径可自定（建议 place=city/town→1、suburb/neighbourhood→0、village→3、square→0），无玩法风险 |
| simRoads 裸格坐标 | data 文件 `simRoads[].p` | **不过 `ll()`**，直接是格坐标；设计案两城各一条，已按冻结 proj 验算（§4.2.5 注释） |
| 自检断言（交主程序） | 编码器 / 数据生成后 | 全部 (x,y) ∈ [0,W]×[0,H]（越界白名单 = §4.2.6 两条）；`kx ≈ W/Δlon`、`ky ≈ H/Δlat`（§4.0） |

## 5. 性能与结构评估

### 5.1 +2 个 geo 文件对首屏的增量

| 指标 | 现状 | +2 城后 | 说明 |
|---|---|---|---|
| `js/` 体积 | 5 个 geo 合计 **4.88 MB** + 其余 0.9 MB ≈ 5.8 MB | ≈ 7.7 MB（**+33%**） | 见 §3.3 推算 |
| `dist/` 总体积 | 11,959,424 B（实测 `build.mjs` 输出） | ≈ 13.8 MB（**+15%**） | Cloudflare Pages 单文件上限 25 MB，`build.mjs` 会校验 |
| **JS 解析增量** | — | **约 +10~30 ms** | geo 文件是**纯对象字面量**（无 IIFE 逻辑），V8 解析 1 MB 字面量约 5–15 ms；两文件合计 |
| `Geo.init()` 成本 | **不增加** | 不增加 | `Geo.init` 只在 `useMap` 切图时对该图解码一次，且有 `cache`（`geo.js:44,49`）按 `CM.GEO` 对象缓存；新城只在玩家选中时才解码 |
| `Game.create` 成本 | gz 实测 **7.3 s** | 每城独立，不叠加 | 新城按自身 W×H 与 zones 计 |

**结论：+2 城的首屏代价 = 约 2 MB 下载 + 10~30 ms 字面量解析；不增加任何运行时模拟成本。** 在桌面 Chrome 基线（README §运行与存档）下可忽略。

### 5.2 数据驱动直加 vs 懒加载改造

**推荐：数据驱动直加（零核心改动）。** 依据：

1. `maps.js:36-44` 的 `for (const m of CM.MAP_LIST || [])` 会自动完成：CFG 白名单替换（`CFG_KEYS`）、`deriveChoice` 发展阶段平移、`macro` 启用判定、`mapFp` 计算（`maps.js:46-50`）。**新城市只需 push 一个 MAP_LIST 条目。**
2. **懒加载改造是架构变更且高风险**：`maps.js:66 CM.GEO = m.geo` 与 `data_*.js:6 const G = CM.GEOS && CM.GEOS.<id>` 都在**加载时**求值；改成按需注入要重写地图注册时序，并让 `index.html` 的 40 个 script 依赖序出现分支，违背「顺序即依赖声明」的现有约定。
3. 收益（省 2 MB）远小于风险。Cloudflare Pages 有 br/gzip 压缩，实际传输更小。
4. **触发再评估的条件**：城市数超过 ~10 个、或单城 geo 超过 3 MB。届时建议的动态注入点是 `index.html` 尾部按 `MAP_LIST` 循环插 script，仍保持 `maps.js` 之前。

### 5.3 编码器是否值得固化为 `scripts/encode-geo.mjs`

**值得。** 理由：① 源数据（OSM）会更新、bug 要修、抽稀阈值要按 gz 样本校准（§3.4 的 T1/T2/T5/T6 仍开），一次性 `/tmp` 脚本必然丢失；② 两城 + 未来城市复用；③ 与 `scripts/build.mjs`（部署校验）同目录，职责分明。

接口建议（供主程序实施，**本轮不创建该文件**）：

```
scripts/encode-geo.mjs
  入参: --city sz|xa --raw data/raw/<city>/*.json --out js/geo_<id>.js
        [--proj "lon0,lat0,kx,ky"] [--simplify 0.08] [--report]
  输出: js/geo_<id>.js（挂 (CM.GEOS = CM.GEOS || {}).<id>）
        + 统计报告（各层条目数、names 数、文件字节、与 gz 基准对比）
  依赖: 仅 node:fs / node:path；编码逻辑内联（不 import 游戏 js，保证可独立复跑）
  校验: 写盘后自校验——用内联 dec() 解回，断言条目数/点数一致、无 NaN、bbox 在 [0,W]×[0,H]
```

同时建议把 §2.3 的抓取脚本固化为 `scripts/fetch-geo.mjs`（分块 + 断点续跑 + 缓存），与编码器配对。

### 5.4 渲染风格核实

**核实结论：苏州 / 西安均属「中国内地」，无需补 `render.js` / `agents.js` 地区风格表。**

依据：
- `js/render.js:977` `const REGION_KEY = { '中国内地': 'cn', '中国香港': 'hk', '中国台湾': 'tw', '日本': 'jp' }`；`:979 regionKey() { return (m && REGION_KEY[m.region]) || 'cn' }`
- `js/agents.js:25` 同一张表（**两处独立定义，数值一致**）
- `js/data_hz.js:159` 已示范：`region: '中国内地'`

→ 新 data 文件设 `region: '中国内地'` 即自动走 `cn` 风格（车辆配色 `VCOL.cn`、楼宇 `bldStyle` 等），**render.js / agents.js 零改动**。

> 《地图设计指南》§7「新地区需补 render.js / agents.js 的地区风格表，不能直接沿用内地风格」——该句针对**非内地新地区**（如新增日本/香港城市）。苏州、西安不适用。若后续要加东京/香港第二城，才需要补风格。
